Skill 1 · Register

Build the register from the project manual

A script reads the manual's structure and pulls every submittal requirement. Claude applies the project's Division 01 rules, fills gaps and flags what it is unsure about.

You give ita specification PDF, and optionally install dates by spec section.You geta register in Excel, CSV, JSON or Google Sheets values. Each row cites its spec section, paragraph and page.

How it works

1

Read the manual

A script indexes the manual's sections, finds each submittals article, and splits it into items with the spec section, paragraph and page.

2

Apply judgment

Claude reads the Division 01 rules, adds closeout and administrative items, merges related ones, and flags what it is unsure about.

3

Build the register

The register is stored as plain data and written out in the format you choose. The Excel version has project rules, a review queue and a section summary, with date formulas that update when you enter install dates.

How it was tested

15public documents, from a 2-page attachment to a 776-page manual
2,300+submittal items extracted across them
98%of an owner's 1,519 submittal lines found on a two-volume federal specification
0lead times guessed. Dates and lead times are always inputs.
Check the work. The skill flags what it is unsure about, but a person should confirm those rows and spot-check pages against the manual before the register is issued. Read the verification guide.

What it does not do

Limits

  • It does not read scanned PDFs. It needs a text layer.
  • It runs one file at a time. For split volumes it lists every section it could not find.
  • Submittals written inside construction paragraphs come through as review rows, not finished rows.
  • The Google Sheets output follows the connector's format but has not been run against a live sheet.

How to check a register

  • Page-check ten random rows against the PDF.
  • Read the Review Queue. Each flag says why.
  • Compare rows per division with the table of contents.
  • Recompute three dates by hand.

Try it

  1. Download the Register skill and unzip it into your Claude skills, or copy the submittal-register folder from GitHub.
  2. Attach a project manual PDF and ask for a submittal register.
  3. Optionally give install dates by spec section so required submit dates calculate.
python3 scripts/extract.py manual.pdf draft.csv
python3 scripts/build_register.py reviewed.csv \
  Register.xlsx --rules rules.json \
  --save-json register.json

Skill 2 · Intake

Update the register from a transmittal or a stamped return

You choose the project by choosing its register, then upload the documents. Claude reads them, and code decides where each change goes and whether it makes sense.

You give itthe register (register.json) and one or more transmittals or stamped review returns.You getthe matching lines updated with status, dates, revision and ball in court, a backup of the register, and an audit log.

How it works

1

Read the document

Claude turns each document into events: sent for review, or returned approved, approved as noted, revise and resubmit, or rejected.

2

Match to the register

The matcher finds the register line from the spec section and the wording. Lines that read alike, items not in the register, and documents whose project does not fit the register go to you. Nothing is guessed.

3

Apply and log

Each change is checked, written to the register, and added to an audit log, with a backup kept. Uploading the same document twice changes nothing.

How it was tested

Two public registers and four sample documents. With the wording shortened, reworded and put in plural on registers of 51 and 243 lines, the matcher was never confidently wrong. It asked a person about a small share of lines that read nearly alike. It has not been tried on real project paperwork yet, so the first real documents are the real test.

What it does not do

Limits

  • It has no OCR, so scanned stamps are read by eye and are worth a second look.
  • It does not read Gmail yet. Each project needs its own label or sender list first, so that a submittal cannot land on the wrong project.
  • It updates registers saved as register.json, which the Register skill writes with --save-json.

Safeguards

  • Wrong project: a document whose project name does not fit the register is held back.
  • Out of order: a return with no earlier submission is reported as a conflict, not applied.
  • Repeats: the same document uploaded twice changes nothing.

Try it

  1. Download the Intake skill and unzip it into your Claude skills.
  2. Choose the register, then upload a transmittal or a stamped return.
  3. Or start with the four fictional sample documents in the repository: a transmittal, a typed review return, a scanned stamped cover sheet and a transmittal for a different project.
python3 scripts/intake.py match register.json events.json -o matches.json
python3 scripts/intake.py apply register.json matches.json --dry-run

Skill 3 · Compare

Compare two registers and see what changed

The script pairs up the submittals in the two registers and drops the noise. Claude settles the borderline pairs and writes the summary.

You give ittwo registers for the same project (Excel, CSV or register.json) and which one is old.You getthe size of the change as counts and percentages, what was added, deleted, moved or modified, and a workbook of the details.

How it works

1

Match the two registers

Submittals are paired within each spec section, then across sections for anything that moved. Case, plurals, punctuation, row order and numbering are ignored.

2

Classify the differences

Each difference is added, deleted, moved to another section, or changed in type or approval requirement. Status and date changes go on their own sheet.

3

Summarize the change

Claude settles the borderline pairs and opens with how many submittals matched and what percent of each register is unchanged, modified, deleted or added. Then the big picture: a new section, a block of items that changed type.

How it was tested

1,519lines in an owner's register, compared with 1,556 in one generated from the specification
97.1%of the owner's lines unchanged, 0.9% modified, 2.0% deleted
4.4%of the generated register added, most of it rows still flagged for review
86wording-only differences counted but not listed
One real pair so far. The figures above come from a single project, and the matching was adjusted while looking at it. Automated tests check that known added, deleted, moved and modified items are found and that reordering, renumbering and rewording are not reported.

What it does not do

Limits

  • An item that is both renamed and moved to another section shows as one deleted and one added.
  • Items that repeat in several places, such as one product under product data, samples and O&M, pair in order and can land on the wrong twin.
  • It does not read PDFs. A PDF register must be turned into rows first.
  • It compares the registers as written. It does not say which one matches the specification.

What counts as a difference

  • Added or deleted: a submittal in one register and not the other.
  • Moved: the same submittal under a different spec section.
  • Modified: a changed type, a changed approval marking, or a materially different description.
  • Ignored: case, plurals, punctuation, word order, extra detail in a description, row order and numbering.

Try it

  1. Download the Compare skill and unzip it into your Claude skills.
  2. Give Claude both registers and say which one is old.
  3. Read the summary, then open the workbook for the details.
python3 scripts/compare_registers.py \
  old.xlsx new.xlsx \
  --xlsx Register-Comparison.xlsx \
  -o compare.json
